# Evaluation: what was measured and what the results support

## Evaluation approach

The final report describes stakeholder usability feedback, prototype refinement, task-related measures and a System Usability Scale (SUS) calculation. The target-specification appendix plans several tasks around six users. The presentation separately reports ten interview participants. The final materials do not supply a complete participant-level testing dataset, so those counts should not be combined or described as a verified final-test sample size.

## Selected reported values

| Measure | Reported value | Interpretation |
| --- | --- | --- |
| Intuitiveness | 4 on a 1–5 scale | A perceived-ease rating; not the SUS total and not 80% task success |
| Standard navigation task | 30 seconds | A saved task-time result; no measured before/after reduction established |
| Access to a status link | 20 seconds | A saved timing; earlier definitions also use percentage-based success, so direct comparison needs care |
| Role-specific tasks | 60 seconds for manager tasks; 105 seconds for student tasks | Different role tasks; not proof that one role or interface is faster |
| SUS | 70 on the 0–100 scale | The reported questionnaire calculation; not 70% usability or an established aggregate across all users |

The report's scoring table totals 28 adjusted points and multiplies by 2.5 to obtain 70. The materials do not document an aggregate distribution or confidence interval. The table presents reordered question statements. A future administration should retain a consistent validated questionnaire and scoring procedure.

## Targets and document differences

- The report's original navigation specification sets a marginal threshold of less than 25 seconds and an ideal threshold of less than 15 seconds. The presentation instead shows a marginal threshold of less than 50 seconds. The saved 30-second result is slower than both documents' ideal target and the report's original marginal target. It should not be summarized as meeting all specifications.
- Some original percentage/count measures are reported later as timings. Filtering is described as preconfigured rather than a measured accuracy result. These entries do not support a clean claim that all initial targets were achieved.
- A 40% satisfaction improvement and May 1 integration date are mission-statement goals. They are not measured implementation outcomes.
- Dashboard example values (resolution time, ticket counts and trends) are prototype content, not an operational performance dataset.

## How feedback informed a design decision

The report describes stakeholders wanting tickets to dominate the home page, especially unresolved and in-progress work. This supported moving ticket attention ahead of secondary dashboard content. The learning is the connection from workflow feedback to information hierarchy; the materials do not quantify a causal reduction in resolution time from that change.

## Next evaluation I would plan

1. Define role-specific scenarios and a consistent task script.
2. Record the same task success criteria, time units, error definitions and target version for each run.
3. Capture participant-level outcomes without identifying participants publicly.
4. Use a consistent SUS administration alongside task observations and follow-up questions.
5. Compare the next iteration with the same tasks and report sample size and variation.
6. Evaluate integration and accessibility separately before operational rollout.
